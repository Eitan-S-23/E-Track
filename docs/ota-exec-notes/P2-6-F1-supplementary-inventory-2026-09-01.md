# P2-6 遗留项 F1 处置：R9 证据根附加清册

日期: 2026-09-01
执行: P2-6 非实现独立验收会话（收口后附加，纯增量）
产物: `docs/ota-exec-notes/P2-6-SD-R9-supplementary-inventory-2026-09-01.json`

## 1. 为什么不能用「修上游 manifest」来关闭 F1

F1 记录的对象是 R9 实现会话产出的
`.cache/p2-6-sd-r9-20260901-01-implementation/result.json` 中的 `files` 申报数组。
该文件已按 `artifacts/r9/r9-result.json` 收进 P2-6-v3 冻结证据包并被 SHA-256 绑定。
重写它会改掉已冻结包内的字节，等于事后篡改已收口证据——与
`docs/ota-exec-notes/P2-6-v3-freeze-and-validator-selftest-2026-09-01.md` §9 的禁令同类。

因此 F1 的正确处置不是"修"，而是**增量补一份独立清册**：不动任何冻结字节，
把 R9 证据根的真实全量与两个已有集合做交叉分类，使缺口从"存在但未量化"
变成"已逐条枚举并绑哈希"。

## 4. 定性：申报缺口，非完整性缺口

C 类三项均在冻结包内**按 SHA-256 独立绑定**——即验收会话当时已自行读取
并哈希了这些文件，未依赖上游申报。故 F1 是**上游申报不全**，
不是**下游证据不可信**；P2-6-v3 的 27 条判据结论不受影响。

附带取得一项实质旁证：`tmp/BAD-2.8.2.etu`（上游已申报，`EA7C5CA2…`，282355B）
与 `tmp/p2-6-sd-r9-bad-upload-hw-02/readback.bin` **逐字节等价**
（同字节数、同 SHA-256）。即 BAD 包经 SD 上传后回读无差异，
C7「升级中途失败」的失败点确实落在 worker 校验而非传输损坏。

## 6. 本清册的局限（必须随清册一起引用）

- 哈希取值时点为 **2026-09-01 收口后**，**不构成**对 R9 执行当时文件状态的
  追溯性完整性证明。真正的时点锚是冻结包内那 62 项。
- 本清册**不修改** P2-6-v3 合同、证据矩阵或包内任何字节，
  也**不改判** P2-6 的 PASS 结论。
- 本清册**不使** F1 从"遗留"变为"已闭合"：若后续轮次要复用 R9 证据，
  仍应以冻结包内已绑定项为准，D 类不得直接充当判据输入。
