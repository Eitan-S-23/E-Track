## 2. 方向性纠正：目标设备的广播名是 `XTrace`，不是 `iGPSPORT`

上一轮（及更早）把检索目标写成 `igpsport|BSC300|fff0`，**这是错的**。
`iGPSPORT BSC300_1234` 是**演示页 `speedometer_page.dart` 里的字面量**（上一轮报告 §1 已记录），
不是固件行为。固件侧的真实定义是：

| 事实 | 位置 |
| --- | --- |
| BLE 模块名由固件下发 `AT+NAME=XTrace` | `USER/HAL/HAL_Bluetooth.cpp:234`（`HAL::BT_SetName()`） |
| BLE 走 **UART 外部模块**，不是片内 BLE | `USER/HAL/HAL_Config.h:92` `CONFIG_BT_SERIAL = Serial`；`:95/:96` `CONFIG_BT_TX_PIN=PA9` / `RX_PIN=PA10`（USART1） |
| 非透传模式 | `USER/HAL/HAL_Config.h:93` `CONFIG_BT_USE_TRANSPARENT 0` |
| 模块使能脚未使用 | `USER/HAL/HAL_Config.h:97` `//#define CONFIG_BT_EN_PIN PA15`（已注释） |
| App 侧不认识该名字 | `app/bluetooth_flutter_Trace/lib` 中 `xtrace`/`x-trace` 命中 **0 个文件** |

两个直接后果：

1. **检索关键词应为 `XTrace`**，`iGPSPORT` 系列关键词对本装置无效。
2. **「MCU 存活」推不出「BLE 在广播」**：广播由 UART 外部模块负责，
   其供电与状态独立于 MCU。上一轮 J-Link 证明的只是 MCU 侧（VTOR、SysTick、
   应用全速运行），**对 BLE 模块的状态没有任何覆盖**。

## 3. 方法学纠正：App 的日志出口在 **5 台**处饱和

本轮统计（`logcat-r2b.txt`）：

```text
获取设备名称，设备ID           1044 行
扫描结果中设备名称             1044 行
去重 MAC 仅 5 个，每个约 209 行：
  08:38:E6:59:63:27 / 4F:07:2F:B2:7A:FC / 68:E4:78:9E:CA:A0 / AE:02:22:37:82:3E / F3:8A:B8:18:1B:F7
去重名称仅 2 个 + 1 个空：AJBLE94、U-EWHCA9F、（空）
同时 BleController 报告的设备总数：11 / 12 / 13 / 14 / 15 / 16 / 17
```

即：**扫描到 17 台，日志只吐 5 台**，恒定饱和。

**这推翻了上一轮报告的 §3.2**：那份报告写「15:55–16:08 连续扫描，去重后仅 5 个地址」
并据此判定「目标板未出现」——那个"5"是**日志出口上限**，不是扫描结果本身。
当时没有 UI 侧清单做交叉验证，该判定**不成立**，现予以更正。

**因此本轮的日志同样不能用来证明「板子没广播」。** 权威出口只剩 UI 列表。
