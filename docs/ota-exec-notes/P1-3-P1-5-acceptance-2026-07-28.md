这些结果证明底层 bootstrap、BCB 首次建立和 recovery 剥尾机制可工作，但不能
消除顶层一键部署脚本的安全性问题。

### 阻断项 1：legacy 回退可能恢复错误 HEX

`deploy-ota-bootstrap.ps1` 先复制用户传入的 `LegacyHex`，随后又复制仓库默认
`MDK-ARM_F435/Objects/X-Track.hex`，目标目录只保留 basename，并使用 `-Force`。
当两者同名时，用户明确选择的旧布局恢复资产被仓库默认文件覆盖；catch 路径再
从该被覆盖文件恢复。

用不同内容的同名样本独立复现结果：

```text
P1_5_LEGACY_COLLISION_RESULT=REPO_DEFAULT
```

因此失败回退有刷错镜像风险，阻断一键迁移验收。

### 阻断项 2：正常启动可假阳性

部署脚本读取普通 reset 的 VTOR、CFSR 和寄存器，但 PASS 谓词只检查 VTOR、
早期 `OTA: HANDOFF` RTT 行及 BCB。HANDOFF 输出发生在 HAL/App 初始化之前。
将 reset 证据中的 CFSR 构造成 `00010000` 后，当前全部 PASS 谓词仍成立；也就是
App 在 HANDOFF 后 HardFault 仍可能输出 `P1_5_DEPLOYMENT=PASS`。

### 阻断项 3：recovery 可原地破坏源资产

`prepare-bootstrap-app.py` 仅在检测结果为 App 时拒绝 input==output；有效 recovery
输入会先剥除尾部 8B，再写回同一路径。独立复现：

```text
valid recovery input: 1544B
command result: exit 0 / PASS
same source after command: 1536B
```

源 recovery 容器的长度/CRC trailer 被永久删除，违反资产保留与失败恢复预期。

### 阻断项 4：实现越过冻结范围

P1-5 卡冻结范围是 `tools/` + `docs/`。实现提交还修改了 workflow、CMake、Boot
linker，并新增生产 `boot/**` 命令协议和 QSPI 写路径；`PLAN-OTA-EXEC.md` §9
没有范围/契约变更登记。验收会话不能事后把越界实现解释为原范围内交付。

### 阻断项 5：fresh legacy AC5 构建失败

按 AGENTS.md 使用 uVision 完整构建 legacy target `X-Track`，fresh 源码得到：

```text
compiling ota_vtor_check.c...
ota_vtor_check.c(8): error #35:
  "ota_vtor_check.c is only valid for an OTA App target"
1 Error(s), 0 Warning(s).
Target not created.
```

项目 XML 表面上没有把 OTA App 文件加入 legacy target，但 uVision 生成的 legacy
dep 实际包含它；不在本验收会话修复或擅自重开 P1-2。当前结果意味着无法从
fresh 当前源码独立复现“纯 AC5 旧布局 -> 一键迁移”的前置旧布局构建。

### 结论

P1-5 验收不通过，保持 `进行中`。上述脚本安全性、范围登记和 legacy AC5 构建
问题修复后须重新独立验收。
