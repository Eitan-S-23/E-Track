## 3. 阻断级缺陷

### 3.1 【阻断 F4-a】截断提示在最危险场景下不触发，且反馈错误信息

`FirmwareUpdate.cpp:611-628`：

```c
if (scanCount >= SCAN_MAX) { scanLimited = true; }
...
if (rowCount == 0u || (rowCount == 1u && rows[0].isUp))
{
    SetBrowserMessage(pathTooLong ? TXT_PATH_LONG : TXT_EMPTY, "");  // TXT_EMPTY = "未找到 ETU"
}
else if (pathTooLong) { SetBrowserMessage(TXT_PATH_LONG, ""); }

if (scanLimited && rowCount >= ROW_MAX)      // ← 只在列表已满 24 行时才提示
{
    SetBrowserMessage(TXT_SCAN_LIMIT, "");
}
```

**失效场景（正是触发 F4 的那类目录）**：SD 根目录含 300 个非 `.etu` 文件，
`.etu` 排在第 280 位。

1. 扫到第 256 条，`scanCount` 触顶退出，`scanLimited = true`；
2. 这 256 条全被 `!ota_sd_has_etu_extension` 过滤 ⇒ `rowCount = 0`；
3. 截断提示条件 `rowCount >= ROW_MAX` 即 `0 >= 24` **为假 ⇒ 不提示**；
4. 落入 `rowCount == 0` 分支 ⇒ 显示 **`未找到 ETU`**。

**后果**：包明明在卡上，UI 报「未找到 ETU」。这是**静默截断 + 错误反馈**，
直接违反交接提示词 §3.1 对方案 1 的硬要求：

> 「需要同时给用户可见的提示（复用已有的 `SetBrowserMessage` 机制），
> **不要静默截断**。」

**为何定为阻断**：F4 的用户可见故障从「点击即复位」变成「找不到文件」，
用户仍**无法选到 `.etu` 发起升级**，P2-5 卡内硬条件
「真机完整一轮 SD 升级」照旧不可达。症状换了形态，闭环没打通。

**整改方向**：`scanLimited` 应无条件提示（至少必须覆盖 `rowCount == 0`
与 `rowCount == 1 && isUp` 两个分支），且不得被 `TXT_EMPTY` 覆盖。
注意末尾 `SetBrowserMessage` 之间是**后写覆盖**关系，整改时需理清优先级。

### 3.2 【阻断 F4-b】提示词 §3.2 强制量化未做，且跳过理由不成立

交接提示词 §3.2 原文将量化明确划归实现会话（「**这是你的活**」），要求
测出目录条目数、单条耗时、总耗时，据此论证所选上限与喂狗周期的裕度。

实现证据 §量化说明给出的跳过理由：

> 「AC5 构建链因预存问题损坏，**无法生成可烧录固件**做真机 RTT 插桩」

**该理由与事实不符**：

- 第三轮验收报告 §2.1 明确记载：**设备侧 App = GCC Release 编译版本**，
  vcode 20800 —— 真机跑的从来就是 GCC 固件，不是 AC5 固件；
- 本轮 GCC Release 构建**是绿的**，`.elf`/`.bin` 已产出并经本会话核对；
- 故 AC5 能否构建**与真机插桩量化毫无因果关系**，烧 GCC 固件即可量化。

**后果（这才是实质危害）**：`SCAN_MAX = 256` 与「每 32 次喂狗」两个数字，
全部建立在文档自述的**凭空假设**上 —— 原文即写「**假设**单次
`lv_fs_dir_read` ~50ms」。该假设无任何实测支撑：若实际为 200ms，
256 次即 51 秒。参数缺乏依据，等于修复裕度不可知。

## 4. 须一并整改项

### 4.1 SCAN_MAX 上界未把扫描压进看门狗周期

实现证据 §量化说明自述：

> 「`SCAN_MAX=256` 上界：256 次 dir_read **~12.8s（理论上界）**，
> 但配合喂狗不会触发 IWDG」

即方案 1 的上界**并未**将扫描时间压到 10 s 以内，不复位完全依赖方案 2 喂狗
续命。结果是 IWDG 不再复位，但主循环停摆约 12.8 s —— 屏幕冻结、按键无响应。
从用户视角这仍是「卡死」，只是不重启。方案 1 的本意是让扫描时间**本身**可控，
上限值应由 §3.2 的实测反推，而非取一个仍然超时的数再靠喂狗兜。

### 4.2 提示文案数字错误，对用户构成误导

```c
#define TXT_SCAN_LIMIT "SCAN LIMIT 24, USE SUBDIR"
```

文案里的 `24` 是 `ROW_MAX`（可见行上限），但触发这条提示的是
`SCAN_MAX = 256`（扫描条目上限）。两者是不同量纲，用户会理解成
「只能扫 24 个」。文案应反映真实语义（目录条目过多、可能有文件未列出）。

### 4.3 三个文件被注入 UTF-8 BOM

实测（`head -c 3 | od -An -tx1`）：

| `USER/App/Pages/FirmwareUpdate/FirmwareUpdate.h` | `efbbbf` | **BOM** |
| `PLAN-OTA-EXEC.md` | `efbbbf` | **BOM**（diff 首行可见） |
| `USER/App/Pages/Dialplate/Dialplate.cpp`（未改，对照） | `23696e` | 无 |
| `USER/main.cpp`（未改，对照） | `2f2a0d` | 无 |

仓库同类文件均无 BOM，仅本次改动的三个文件被注入。违反全局
`CLAUDE.md`「所有代码文件必须使用 UTF-8 无 BOM 编码进行读写操作」。
须去除（含 `PLAN-OTA-EXEC.md`）。
