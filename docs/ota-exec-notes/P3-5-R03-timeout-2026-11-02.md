### Implementation Contract: Unconfirmed DATA Retirement

This is the task's code-spec record, not a replacement P3-5 acceptance Spec or
an amendment to frozen historical bundles.

#### 1. Scope / Trigger

DATA reached a platform write invocation, but the transfer retires without a
correlated receiver response. A completed platform Future is not a UART frame
receipt; reconnect, cancellation or disposal does not prove receiver framing.

#### 2. Signatures

- `OtaBleTransport._quarantineUnconfirmedData() -> void` checks actual DATA
  dispatch and existing v1 in-flight / v2 framing receipt state.
- `getDeviceInfo({Duration timeout}) -> Future<DeviceOtaInfo>` remains the public
  query; cancelled/disposed instances stay unusable.
- `_getDeviceInfo({Duration timeout, bool allowCancelled})` permits only the
  internal cancellation GET_INFO path to bypass cancellation, never disposal.
- `abortBestEffort({bool allowResync = true}) -> Future<void>` drains the existing
  write queue, then may use the existing bounded query before ABORT.
- `OtaService` calls its abort helper with `allowResync: false` after background
  recheck rejects binding/identity. Ordinary user cancellation keeps the default.

#### 3. Contracts

Quarantine reuses `_poisonedDevices` and `_DeviceWriteLedger.epoch`; no new device
controller, wire message, global query retry policy or timeout is introduced.
`_unconfirmedDataEpoch` distinguishes this transport's retirement marker from an
explicit partial-write failure or another owner's newer poison generation.
Known failed partial writes retain their existing fail-closed behavior; an
ordinary ABORT must not automatically flush them.

V2 `unconfirmedSeqs` records fully dispatched sequence numbers. A CRC-valid,
session/epoch/sequence-matching parsed DATA reply may retire its framing receipt
after cancellation, but cannot reactivate the window, publish progress or clear
quarantine. Credit/durable acceptance remains in the original window validator.

Only the current authoritative recovery query may clear quarantine, after full
INFO payload/identity validation. Matching header/CRC alone is insufficient.
Malformed or unsupported identity is delivered to the waiter as the original
typed error, with quarantine retained. Old physical writes, query sequence,
poison epoch and the existing 20 x 800 ms recovery budget remain enforced.

#### 4. Validation And Error Matrix

| Input / state | Required result |
| --- | --- |
| Cold healthy query | One query; no global retry or new quarantine |
| No DATA was dispatched | No retirement marker from a mere reservation |
| Completed DATA, no receipt, disconnect/error/disposal | Device-scoped quarantine survives wrappers and reconnect |
| Fresh BEGIN while quarantined | WRITE_TIMEOUT before any business bytes are written |
| Normal connected cancellation with unresolved DATA | GET_INFO-only bounded recovery, then ABORT only with valid evidence |
| Cancellation recovery write or identity failure | No ABORT, no DATA, no success; new wrapper remains gated |
| Background recheck rejects binding or identity | No recovery query; if DATA remains unconfirmed, ABORT is also refused |
| Explicit partial-write poison / newer foreign poison epoch | No automatic cancellation recovery; preserve existing isolation |
| Late matching v2 DATA ACK after cancel | Framing bookkeeping only; no credit/session resurrection |

#### 5. Good / Base / Bad Cases

Good: a first GET_INFO is swallowed by the retained DATA prefix; a later valid
matching INFO proves resynchronization, then a fresh transfer completes without
resetting staging. Base: a normal acknowledged cancellation still performs its
ABORT cleanup. Bad: treating `writeChunk` completion, a changed wrapper or a
CRC-valid but unsupported INFO identity as sufficient proof.

### Bug Analysis: P35-R03-RESYNC-01

#### 1. Root Cause Category

E (implicit assumption), B (cross-layer delivery contract), D (coverage gap).
The host's successful write Future was implicitly treated as complete receiver
delivery outside the write-exception path. The executed red covers this software
gap. It does not establish the lost-byte mechanism of the historical R03 device.

#### 2. Why Fixes Failed

1. The first marker-only fix protected recovery but blocked legitimate connected
   cancellation cleanup. Full-suite CI exposed the missing caller behavior.
2. Adding bounded cancellation recovery restored cleanup but also queried a
   binding rejected by background recheck. The caller must carry that prohibition;
   a transport-only fix could not infer the service's failed identity decision.
3. Reviewing the cancellation oracle exposed header-only poison clearance.
   Full INFO identity validation now precedes clearance; negative cases preserve
   both the original error and isolation.

#### 3. Prevention Mechanisms

| Priority | Mechanism | Action | Status |
| --- | --- | --- | --- |
| P0 | Runtime | Keep delivery uncertainty device-scoped across sender replacement | Implemented; CI outcome below |
| P0 | Test coverage | Inject loss after platform success, not only write exceptions | Executed red; expanded regression |
| P0 | Caller contract | Rejected binding/identity forbids cancellation recovery queries | Implemented; CI outcome below |
| P0 | Evidence | Preserve all baseline/regression failures and exact host results | Archived |
| P1 | Documentation | Record framing receipt vs durable receipt vs fresh identity | This code-spec |

#### 4. Systematic Expansion

Similar risks occur at BEGIN/END and in platform transports whose completion does
not prove receiver delivery; these are review triggers, not new verified defects
or permission for a larger protocol redesign. Keep the write queue, receipt
ledger, service owner and identity gate conceptually separate. Run the full caller
suite before calling a local recovery fix stable; do not use expensive physical
campaigns to discover ordinary cancellation regressions.
