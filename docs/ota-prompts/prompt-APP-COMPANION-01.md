## 3. 六项交付范围

### C1 权限申请与后台设置引导

- 首次使用/绑定设备时分步说明用途，再由用户发起系统授权；设置中保留“后台运行与权限”入口，可重新检查和修复。
- 按实际 Android API/target SDK 和功能申请蓝牙扫描/连接、附近设备、通知权限；检查蓝牙开关。定位仅在旧系统扫描或实际定位功能需要时申请，后台定位不作为所有 BLE 功能的默认前提。
- 互联网、开机广播、前台服务类型等开发侧声明与用户运行时授权分开，不把不存在的授权弹窗写进向导。
- 厂商自启动/电池设置按实际可用入口引导，跳转失败有通用设置说明；不要求一律永久关闭全部省电限制。
- 从设置返回后重新核对可读取状态；无法可靠读取的厂商开关显示待确认/待验证，不以“打开过设置页”证明已授权。
- 拒绝、永久拒绝、通知渠道关闭、暂时跳过和后续撤销权限均有明确降级；不反复强弹窗，不阻断无关可用功能。
- 不为 MCU OTA 索取无关的无障碍、全文件访问、精确闹钟或全屏弹窗权限；App APK 自更新的安装授权仍由其原功能按需处理。

### C2 后台伴侣运行

- 首次打开、绑定并获得必要授权后，由用户明确启用后台能力；手机重启后恢复持久任务与设备关联，不以自动打开 App 主页面作为实现。
- 开机接收入口只做必要的状态/调度恢复，不在广播回调中无限扫描或执行长 OTA；实际启动入口必须满足目标 Android 版本的后台启动限制。
- 优先评估系统伴侣设备关联/存在感知及受控扫描，记录实际设备与系统版本支持情况。不能把关联成功、加了 manifest 或展示通知当作后台连接已可用。
- 使用独立于页面的唯一 BLE/任务执行所有者，明确 Flutter 执行引擎或原生执行器的存活责任；页面和通知只是同一状态的展示入口。
- 有效连接、同步或 OTA 所需的前台服务按实际阶段使用正确类型与权限；设备 BLE 阶段不得用 APK 自更新的 `dataSync` 服务冒充 `connectedDevice` 接管。
- 无设备时退避并控制扫描功耗，不依靠高频 Timer、无限重启或无界持有唤醒锁保活。退出、失败和用户关闭后台模式时按当前任务可取消性正确收尾。
- 系统回收后恢复持久任务并重新建立身份；普通后台、锁屏、最近任务划除、系统回收和手机重启分别记录结果。不承诺强行停止、权限撤销、蓝牙关闭后仍继续运行。
- 本卡以 Android 后台能力为实施目标；其他平台保持兼容或明确回退，不把 Android 结果外推到 iOS/Windows 或未验证厂商。

### C3 OTA 检查、缓存、设备通知与用户确认

- 定时、App 手动、MCU 主动请求进入同一个协调器。周期建议默认 12 小时并可配置，最终取值在本卡实施记录确认；系统调度不是精确闹钟。MCU 主动请求绕过长周期等待，仅允许短时防抖及合并同一在途请求。
- 先依据真实 `GET_INFO` 身份使用既有 latest 接口。断连或切设备后旧身份失效，不为了后台下载而放宽机型/硬件/布局/Boot/协议/镜像摘要校验。
- 下载及流量策略可配置；可复用已校验的不可变文件，但重新连接和正式升级前必须核验当前设备、版本、资产兼容性及有效元数据，不能把过期 URL 或旧缓存当最终授权。
- 明确区分检查中、无更新、有更新下载中、校验中、包已就绪、手机不可达、网络失败、不兼容、稍后和升级各阶段。错误不能显示成“已是最新版”。
- App 完成下载校验后，通过 BLE 通知 MCU；设备暂不可达时保留待处理状态，重连核对后再通知，同一固件不持续重复弹窗。
- MCU 的更新入口、状态和提示不依赖手机打开 OTA 页面。用户在 MCU 选择立即更新后 App 才进入正式 OTA，稍后不启动传输；骑行/低电量/关键操作时的提示与安装策略在实施设计中明确。
- 确认绑定设备、目标版本、包摘要和本次操作；旧确认、旧回调、设备切换或包变化不得触发另一升级。正式成功仍以重启后新连接 `GET_INFO` 的目标版本和完整 raw SHA-256 为准。
- 新增“请求检查/检查结果/就绪通知/用户选择”是本卡控制语义设计范围。实现前补齐字段、请求关联、版本/能力协商、超时、幂等、旧端兼容和安全回退；复用现有文本控制通道时必须与二进制 OTA 所有权互斥。若需改变冻结线端协议，先走既有合同增补流程，不就地改冻结字节；保留原传输帧、durable、取消和 Boot 安全语义。
- 若 MCU 请求时手机服务不可达，明确提示连接手机/打开 App，不保证 BLE 按钮能无条件唤醒被强停的 App。后台收到同意后的启动必须有合法且已确认的执行入口，不能直接删除 P3-8 的前台接管/安全回退保护。
- 先完成 E-Track 主控闭环；登记项目各外设的固件身份和实际 OTA 能力，支持的设备按其协议适配。不支持或缺协议的外设明确展示并在本卡列出待定范围，不能仅因有蓝牙就宣称可升级，也不能静默丢掉外设需求。

### C4 MCU 波轮菜单导航修复

- 列出实际一级/多级菜单、设备信息、路线相关页、文件/固件页及弹窗入口，对比正常与异常页面，不能只改用户偶然提到的一页。

- 同时核对焦点注册、事件路由、重复点击抑制、编辑模式、列表容量与页面切换时的组清理/恢复，避免只加入焦点后按下仍无动作，或一次按键触发多次 Pop。
- 空列表、长列表、动态内容、离开后再次进入和弹窗关闭均保持可操作；保留触摸行为及现有安全快捷操作。
- 升级应用等不可退出阶段继续遵守原安全限制，隐藏/禁用按钮不得因为统一焦点而变成可触发；不顺带重构无关页面或渲染性能路径。

## 6. 主入口检查接口（开工前置）

触发点为查询进度、认领和交接；本项目没有 `.trellis/`，本节直接补入既有唯一 Spec，不新增任务框架。

- 签名: 在主目录运行 `python -B Tools/workflow/main_board.py --repo-root <调用方工作区>`；从任务目录调用时使用主目录脚本的绝对路径。
- 输出: JSON 中 `primaryRoot`、`mainRoot`、`board` 给出实际正本位置，`callerBranch`/`callerHead` 给出调用方身份，`localMain`/`remoteMain` 和 `remoteVerified` 表示本次版本核对。
- 成功契约: 根目录确实检出 main 且与新查询远端一致时 `ok=true`、exit=0；本地看板有改动则 `delivery=LOCAL_PENDING`，否则为 `MAIN_MATCHED`。前者不是远端交付成功。
- 失败契约: main 仍绑定缓存目录、绑定缺失/歧义、远端更新而本地未同步、远端不可用或路径重解析均失败，exit=2；不得从旧 origin/main 或聊天补造“最新”。脚本不 fetch、不切分支、不改文件或凭据。

| 用例 | 必须结果 |
| --- | --- |
| 主目录 main、新远端一致、看板无本地修改 | MAIN_MATCHED，返回根目录看板 |
| 任务分支执行，主目录 main 有本地待交付卡片 | 返回主目录而不是任务副本，LOCAL_PENDING |
